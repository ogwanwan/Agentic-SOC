# ④ Triage (트리아지) — 사건 우선순위 게이트

> 담당: 정규화·탐지 파트 / 관련 파일: [`triage.py`](triage.py), [`llm_review.py`](llm_review.py)

## 한 줄 요약
결정론 파이프라인이 만든 **수백 건의 Incident**를, 사건이 이미 가진 사실들로 **점수 매겨 줄 세우고**,
상위만 조사로 보내고 나머지는 대시보드/보류로 라우팅하는 단계.
트리아지는 **2단**이다: **앞단=코드(결정론 점수), 뒷단=LLM(상위 사건 재검토)** — 둘 다 기본 경로.

---

## 1. 왜 필요한가 (Context)

- 실 EC2 로그에서 결정론 파이프라인이 사건을 **수백 건**(테스트 ~225건) 낸다.
- 이걸 전부 LLM 조사로 넘기면 **비용·지연·노이즈가 폭발**한다.
- Triage는 **결정론 구간과 조사 구간 사이의 문지기**다.
  - **하는 일:** 순위 매기기(정렬) + 하위 걸러내기(필터).
  - **안 하는 일:** "진짜 공격이냐?"는 **판단** — 그건 조사(Investigate) 단계 몫.
- 판단을 안 하기 때문에 **같은 입력 → 항상 같은 순위**(재현 가능). SOC에서 중요한 성질: 어제 P1이던 게
  오늘 P3로 바뀌면 신뢰할 수 없다.

전체 파이프라인에서의 위치:
```
정규화 → 탐지(seed) → 사건묶기(Incident) → [④ Triage: 점수·순위·라우팅] → (상위만) 조사
                                               └─── 결정론 여기까지 ───┘   └─ LLM/사람 여기부터 ─┘
```

---

## 2. 점수는 무슨 근거로 오르나 (Score) — 핵심

점수는 **Incident에 이미 들어있는 4가지 사실**만 더해서 낸다. 외부 판단·LLM·랜덤 **없음**.

> 가중치·경계는 실 EC2 로그 285사건 분포로 튜닝(2026-09-26). **심각도가 밴드를 지배**하고,
> 계층/연결 가산은 혼자 밴드를 못 넘게 작게 잡았다(스캐너의 가짜 2계층이 P1로 올라오던 문제 해결).

| 요소 | 계산 | 의미 (왜 위험 신호인가) |
|---|---|---|
| **심각도 (severity)** | 가장 센 탐지룰 등급<br>`critical=50, high=30, medium=12, low=4, 없음=0` | **주축.** 밴드를 지배 — critical이면 그 자체로 P1 |
| **계층 체인 (layers)** | (계층 종류 개수 − 1) × 6 <br>단일계층=0, 2계층=6, 3계층=12, 4계층=18 | web·system·auth처럼 **여러 계층에 걸침 = 공격 체인 진행 신호** (단일계층은 가산 없음) |
| **연결 종류 (join_types)** | join 종류 개수 × 3 | 계층들이 **실제로 이어졌다는 증거**(계보/네트워크 매칭) 종류 수 |
| **seed 수 (seed_count)** | (탐지 수 − 1) × 2, **최대 8** | 같은 사건에 탐지가 **여러 번** = 단발 노이즈일 확률↓ |

**점수 = 위 4개의 합.**

### 실제 예시 — INC-7d29ffde = 70점
```
심각도  50   (critical 룰: 웹루트에 실행 스크립트 기록)
계층     6   (auth + system = 2계층 → (2-1)×6)
연결     6   (audit_lineage + system_auth = 2종 × 3)
seed     8   (탐지 6건 → (6-1)×2=10 → 상한 8)
──────────
합계    70   →  P1
```
이 분해 내역은 각 사건에 **`triage_parts`** 필드로 그대로 남는다(설명 가능성/XAI).
→ **"왜 이게 1순위냐?"** 라는 질문에 언제든 답할 수 있다: *"치명 룰 + 2계층 + 연결 2종 + 탐지 6건 = 70점."*

## 3. 점수 → 어디로 보내나 (Routing)

```
점수 50 이상  → P1 / investigate   ┐  (critical 앵커)
점수 30~49    → P2 / investigate   ┘  상위(P1·P2)만 조사(LLM/사람)로  (high)
점수 12~29    → P3 / dashboard        대시보드에 쌓아둠
점수 0~11     → P4 / hold             보류
```
> 실 EC2 285사건 기준 분포: **P1 29 / P2 249 / P3 7**. (튜닝 전엔 P1이 271로 변별력 없었음)
- **LLM·사람 조사는 P1·P2만.**
- **P3·P4도 버리지 않는다** — 대시보드/보류로 보존. 나중에 패턴 분석·오탐 튜닝에 쓴다(침묵 방지).

출력 계약: `triage(incidents)`는 각 Incident에 아래 필드를 **추가**하고 점수 내림차순 정렬한다.
원본 증거(members/join_path/seeds)는 **변형하지 않는다**.
```
triage_score : int          점수
priority     : "P1".."P4"    우선순위
route        : investigate | dashboard | hold
triage_parts : {...}         점수 분해 내역(왜 이 점수)
```

## 4. 뒷단 — LLM 재검토 (기본 경로)

앞단(결정론 점수)이 상위를 고른 뒤, **그 상위(P1·P2)만** 한 번의 호출로 경량 LLM(**Claude Haiku**)에게
"이거 조사할 만해?" 물어 의견과 이유를 붙인다. **별도 플래그 없이 항상 실행되는 트리아지 뒷단이다.**

- 붙는 필드 (점수·순위·정렬은 **안 바뀜**, 의견만 얹음):
  ```json
  "llm_investigate": true,
  "llm_reason": "웹 프로세스가 웹루트에 스크립트를 쓰고 로그인 계정 생성 — 웹셸→권한상승 체인으로 보임"
  ```
- **몇 건이 LLM으로 가나?** P1·P2 사건 전부, 단 **최대 20건 상한**(`MAX_REVIEW`). P1·P2가 50건이어도
  상위 20건까지만 → 비용 방어.
- **키 없거나 실패하면?**(안전장치 — 옵션 아님) LLM만 건너뛴다고 한 줄 알리고 **결정론 결과가 그대로**
  나간다(상위건이 사라지는 게 아니라 `llm_reason`만 안 붙음). **파이프라인은 절대 안 멈춘다.**

## 5. 실행

```bash
# 기본 실행 — 앞단(결정론)+뒷단(LLM) 둘 다. ANTHROPIC_API_KEY 있으면 LLM 재검토까지 자동
python run_pipeline.py --apache tools/sample_access.log --auth tools/sample_auth.log \
  --network tools/sample_eve.json --audit tools/sample_audit.log \
  --out-incidents out/incidents.jsonl

# 특정 우선순위 이상만 출력/저장
python run_pipeline.py ... --min-priority P2
```
콘솔 출력 예:
```
[triage] priority 분포={'P1': 1, 'P2': 1}
[triage] LLM 재검토 2건(P1~P2 상위)                        # 키 있을 때
[triage] ANTHROPIC_API_KEY 없음 → LLM 재검토 생략, 결정론 결과만 사용   # 키 없을 때
```

## 6. 참고 사항 (팀이 알아둘 것)

- **결정론이다.** 같은 입력 → 같은 점수·순위. 트리아지 자체엔 랜덤/시각/LLM이 안 들어간다
  (`--llm`은 그 위에 얹는 별도 의견 레이어).
- **사건 크기(member_count)는 점수에 안 쓴다.** "큰 것 ≠ 위험." 로그 2만 줄짜리 정상 프로세스 트리가
  진짜 공격보다 위로 오는 걸 막기 위해 일부러 제외. (거대 사건은 `oversized=true`로만 표시)
- **최신성(recency)은 v1에서 제외.** "지금 기준 최근인가"는 재현성(같은 입력→같은 점수)과 충돌.
  넣으려면 배치 내 상대값(결정론)으로 나중에 추가 — open issue.
- **가중치(40/25/10/3, ×10, ×5, 경계 40/20/8)는 튜닝 노브다.** 초기값일 뿐, EC2 실로그 점수 분포를
  보고 조정해야 한다. → **탐지 파트와 조율 필요.**
- **API 키 취급:** `ANTHROPIC_API_KEY`는 `.env`에 넣으면 SDK가 알아서 읽는다. 코드는 키 값을
  **읽거나 출력하지 않는다.** `.env`는 `.gitignore`에 있으니 **절대 커밋 금지.**
- **비용:** Haiku + 상위 20건 상한 + 결정론 사전필터라 사건당 호출이 아니라 배치당 1회 → 미미함.
- **하류(조사 파트) 합의 필요:** 조사 에이전트가 쓸 입력 필드는 `priority` / `route` /
  `triage_score` / `triage_parts` (+ `--llm` 시 `llm_investigate` / `llm_reason`).
